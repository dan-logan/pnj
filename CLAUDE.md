# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A digital implementation of the Pegs and Jokers board game built with React, Vite, and Tailwind CSS. Single-player game where you (Yellow) play against 3 AI opponents (Blue, Pink, Green).

## Commands

- `npm install` - Install dependencies
- `npm run dev` - Start development server
- `npm run build` - Build for production (outputs to `dist/`)
- `npm run preview` - Preview production build locally
- `npm test` - Run the Vitest suite once
- `npm run test:watch` - Run tests in watch mode

## Architecture

The rules engine is pure JavaScript (no React), separated from the UI so it can be unit-tested and reused:

- **src/game/constants.js** - Card values, board dimensions (72-space track, 18 per side), player colors/names. Also `GAME_MODES`, `TEAMS` (partners 0+2 vs 1+3) and the `getPartner`/`sameTeam` helpers used by partner mode
- **src/game/deck.js** - Deck creation (two 52-card decks + 4 jokers), shuffling, drawing with discard-pile reshuffle
- **src/game/engine.js** - Move validation (`isValidMove`, `hasAnyValidMove`), move application (`applyMove`), win detection, animation paths, UI affordances (`getValidDestinations`, `getMovablePegs`, `findBumps`). All functions take the peg state as an argument and return new state without mutating. Movement functions accept an `options` arg (`{ actor, mode }`) so a player can move a partner's pegs and so the partner friendly-bump rule applies; `applyJoker` supports partner mode, and `checkWinner(pegs, mode)` returns a team index in partner mode. The move appliers also return `displacements` — the engine's own account of every peg the move shoved off a space, and the only reliable source for friendly partner bumps (see "Following the game")
- **src/game/ai.js** - AI move enumeration and scoring (`getPossibleMoves`, `findBestAIMove`); prioritizes moves that advance toward home, avoids vulnerable positions. In partner mode it scores by team distance, plays for its partner once its own pegs are all home, and values friendly-bump jokers
- **src/game/stats.js** - Persistent player statistics in localStorage; pure record/derive logic with an optional injectable storage backend. `didIWin`/`winningSeats` interpret a winner correctly per mode (classic: a player index; partners: a *team* index). `recordFinishedGame(gameId, result)` is idempotent, deduping on `pnj:recordedGames:v1` (FIFO, capped)
- **src/game/status.js** - Pure derivation of what the game is doing and how it reads: `derivePhase`, `describeStatusParts`/`describeStatus`, `describeCard`, `describeOutcome`. See "Game phase and status" below
- **src/game/announce.js** - Pure derivation of which on-screen banners a move earns (`announcementsFor` → Joker! / Partner Bump! / Double Play!), plus the speech-bubble texts (`@$#*!`, `Thanks!`, `You're welcome!`) and the on-screen durations. See "Following the game" below
- **src/game/events.js** - `diffPegEvents(oldPegs, newPegs)`: what visibly happened across a move — `cameOut`, `reachedHome`, `finishedAll`. Pure; the engine already reports bumps, this covers the other two things you'd hear at a real table. See "Following the game" below
- **src/anim.js** - The animation pacing table (`SPEED_SETTINGS`: `stepMs`/`thinkMs`/`settleMs` per speed), the `slow → normal → fast → off` cycle, and the persisted preference (`pnj:animSpeed:v1`, injectable storage). `animationsOn(speed)` is the one derivation of the old on/off boolean. Also the bump fly-back's own pacing (`BUMP_FLY_*`, `stageBumpFlights`), which is impact feedback rather than travel and so isn't tied to the speed setting
- **src/net/seats.js** - Pure seat-ownership helpers, no React: `mySeatsOf`, `primarySeat`, `isMyTurnFor`, `isAISeat`, `nextHumanSeat`, the board-rotation math `visualSideFor`/`seatAtVisualSide`, and the `SOLO_/HOST_/GUEST_SEAT_OWNERS` layouts. See "Seat ownership" below
- **src/net/firebase.js** - Firebase config from `VITE_FIREBASE_*` env, `isMultiplayerConfigured()`, and the single lazy `import()` of the Firestore/Auth SDK (`getFirebase`). A solo player never triggers it. See "Remote play" below
- **src/net/protocol.js** - Pure wire-document builders that mirror the security rules exactly (`buildCreateMeta`/`buildJoinMeta`/`buildPublishMeta`, `isEcho`, `waitingSeatOf`, `STATUS`, seat constants). Heavily tested because a shape mismatch here is a rejected write
- **src/net/gameCode.js** - The 6-char join-code generator over an unambiguous alphabet (no 0/O/1/I/L); pure, injectable randomness
- **src/net/session.js** - The remote session client (the §2.5 interface): `signIn`, `createGame`, `joinGame`/`joinGameById`, `fetchGame`, `startGame`, `publishState`, `subscribeGameMeta`/`subscribeGameState`/`subscribeMyGames`. Talks to Firestore through an injectable backend (in-memory fake in tests). Stores the live state/replay as JSON blobs — Firestore can't hold the nested arrays in the game state
- **src/net/localSession.js** - The device's local cache/nickname store of its remote games (`pnj:games:v1`): labels, per-game seat, archive flag, `activeId`. A cache, not the source of truth — Firestore's `participants` is
- **src/net/lobby.js** - Pure lobby derivations: `buildRemoteRows`/`sortLobbyRows` (your-turn first, then recency), `countWaitingOnMe` (the badge), `relativeTime`, and `openActionFor` (what opening a game should do: `adopt` / `deal` / `await_guest` / `await_deal`). "Your turn" is `waitingOn === seat`, never `currentPlayer`
- **src/game/persistence.js** - Save/resume of an in-progress game to localStorage (`serializeGame`, `saveGame`, `loadGame`, `clearGame`, `isResumable`). Snapshots pegs/hands/deck/discards/currentPlayer plus split state, per-game stat tallies and the game's `gameId` as plain JSON. Same injectable-storage pattern as stats.js; no-ops without storage
- **src/audio.js** - Web Audio synth sound effects + `navigator.vibrate` haptics with a persisted mute setting; all no-ops outside a browser. `PLAYER_TONES` gives each seat its own base pitch, so every sound says *who* as well as *what*. See "Following the game" below
- **src/badge.js** - `navigator.setAppBadge` wrapper putting the waiting-on-you count on the home-screen icon (`syncAppBadge`, `isBadgeSupported`); injectable navigator, swallowed no-op wherever badging is unsupported. See "Turn signalling" below
- **src/PegsAndJokers.jsx** - React component: game state via hooks, turn flow, input handlers, SVG board rendering. Turn gating, actor identity and board orientation all derive from `seatOwners` (see "Seat ownership"). Move input is tap-driven: selecting a card glows the movable pegs (`getMovablePegs`), selecting a peg with a 7/9 renders tappable ghost destination circles (`getValidDestinations`). A `useEffect` snapshots the game to localStorage after every committed change and clears it on win; on load it offers a "Resume game?" modal when a save exists. **Instant replay:** each AI move (and stuck-discard) is recorded into a `replayLogRef` buffer as a frame (`{ player, description, pegsBefore, pegsAfter, segments }`); the buffer resets when you hand off your turn and holds exactly the opponents' moves since your last turn. When it's your turn the header's 📺 button (always mounted; see "Following the game") plays them back slowed down, driving the board from the recorded peg snapshots (reusing `calculateMovePath`/`animatingPeg`) and restoring the live board when it finishes or you press Stop. Interaction handlers and the persistence effect are gated on `isReplaying` so playback never mutates the real game or save
- **src/InstallPrompt.jsx** - Dismissible "Add to Home Screen" banner: replays the captured `beforeinstallprompt` on Chrome/Android, shows manual Share-sheet instructions on iOS Safari, hidden when already installed
- **src/main.jsx** - React entry point
- **src/index.css** - Tailwind imports plus small keyframe animations for peg glow/ghost destinations

### Seat ownership

The component never assumes "the local human is player 0". A single `seatOwners` state array says who owns each of the four seats **from this client's point of view**:

| Layout | `seatOwners` |
|---|---|
| Solo (today's only mode) | `['me', 'ai', 'ai', 'ai']` |
| Remote host | `['me', 'ai', 'them', 'ai']` |
| Remote guest | `['them', 'ai', 'me', 'ai']` |

Everything else is derived from it (helpers in `src/net/seats.js`):

- `mySeats` — every seat this client controls, **an array** even though only one seat is ever owned today, so a client driving two seats needs no second refactor. `ownsSeat(p)` is the membership test.
- `mySeat` — the primary seat: whose hand is shown, who acts as the engine `actor`, and whose board edge faces the player.
- `isMyTurn` — replaces every `currentPlayer === 0` turn gate.
- Board rotation — seat `x` is drawn on visual side `(x - mySeat + 2) mod 4` (0 top, 1 right, 2 bottom, 3 left), so your own seat is always at the bottom. `getTrackPosition` / `getStartAreaPosition` / `getHomePosition`, the discard-pile corners and the four board labels all go through `visualSideFor` / `seatAtVisualSide`. With `mySeat = 0` this collapses to the original `(x + 2) % 4`, which is why solo rendering is byte-for-byte unchanged.

Solo is not a special case in the code — it is just the layout whose only non-AI seat is seat 0.

### Game phase and status

The status line is **derived, never set**. `gameMessage` used to be imperative state written from ~40 call sites, several on 800–1500 ms timers; every win path set `winner` and returned *before* touching it, and the timers then fired after the game ended and overwrote the result — which is how "Blue is thinking…" ended up under a win banner. Instead:

- `phase` (`derivePhase`) is the single answer to "what is happening": `finished` → `replaying` → `dealing` → `my_turn` → `waiting_partner` / `ai_turn`, in that precedence.
- `statusLine` (`describeStatus`) renders the phase, folding in the split remainder, joker mode and discard mode — and, since the commentary moved here, the move on screen and the replay frame too (see "The status line is the commentary" below).
- `notice` is the only imperative text — transient feedback like "Invalid move. Try again." — and clears itself on any phase change.
- `describeOutcome` phrases the result for the mode and the seat: "You and Pink win!", "Blue and Green win."

There are no status timers left. Don't add one; if something needs saying, derive it from state.

### Following the game

The game used to be very hard to *watch*. Pegs crossed the board at 150ms a space with no sound, opponents' turns ran together, and the only record of what anyone had done was 8px grey SVG text on the board rim. Everything below exists to make the game legible to someone who isn't already fluent in it — which is most people, and nearly everyone playing on a tablet across a kitchen table.

**Pace is a setting, not a boolean.** `src/anim.js` holds the whole timing table and **`slow` is the default**: 320ms per space, a **2000ms** thinking pause before an AI plays, and a 450ms settle beat after each move lands. The think pause is that long deliberately — the "Blue is thinking…" line and the seat's colour have to be *read*, not glimpsed, and a player who has just looked up from their hand needs time to find the board again before anything on it moves. At two seconds it reads as an opponent deliberating rather than as lag; the rest of the ladder follows it down (1200/400/300). The old control was on/off, which meant the only escape from a peg you couldn't follow was no animation at all. `animationsEnabled` is now derived (`animationsOn(speed)`) so the dozen existing "are animations on?" questions still have exactly one answer, and no second piece of state can disagree with the speed.

**Pegs count themselves along the board.** `animateMove` already stepped one space at a time; it now plays `sfx.step(player, index, total)` on each one — a click per space, pitched to the mover's seat, creeping up as the count goes and landing on an accent for the final space. The board draws the count as a number over the peg, the spaces already crossed as a fading trail, a dashed ghost on the space it left, and a halo under the peg itself. Between them you can look away and look back and still see where the peg came from and how far it has got.

**The count must equal the card — `calculateMovePath` and the home entrance.** The engine models home entry as: the step that would land on `homeEntrance + 1` is instead the step into home slot 0, which is what makes the final slot `homeSteps = amount - stepsToHome`. So `homeEntrance + 1` and home slot 0 are *the same step*, and the path must draw one of them, never both. It used to draw both — the track loop ran `step <= stepsToHome` and the home loop then started again at slot 0 — so every home entry animated `amount + 1` spaces and counted itself out one too high. Green on its own entrance (57) playing a 5 into Home 4 stepped 57 → 58 and then through all five home slots, counting one through six, while the committed move was correctly five. The track loop stops at `step < stepsToHome`; `path.length === amount` for every home entry, which is what the on-board count, `sfx.step`'s `total` and `landingDelayFor` all read.

**A peg that is mid-glide is drawn exactly once.** `isPegAnimating(player, pegIndex)` makes its start slot, its home slot and its track space all render empty while the animation layer draws it. This matters more than it sounds: see the next paragraph.

**Human moves animate *after* they commit — `playMoveVisual`.** Only AI moves used to animate; your own peg teleported. Making human moves animate the normal way would mean unpicking `executeMove`/`completeSplit`/`handleJokerTarget`, each of which validates, applies, checks the winner, records stats and publishes to the wire in one synchronous pass — putting the wire protocol behind an animation timer, for a cosmetic gain. So the state commits first and `playMoveVisual` replays the glide over the already-final board. Two consequences, both load-bearing:

- The real peg is at its *destination* during the playback, which is why `isPegAnimating` hides it — otherwise you'd see two of the same peg.
- `visualBusy` gates the AI effect, so opponents don't start moving over the top of your peg. It is also what spaces consecutive AI turns apart: `completeAIMove` holds it for `settleMs`. Anything that can strand it — `endGame`, `clearBoard`, `startGameWithPlayer`, `applySavedGame`, unmount — clears it explicitly. **A `visualBusy` left true is a game that never takes another turn**, so every new exit path from a move must clear it.

**Everything a move causes is deferred to the moment the peg lands, because the two kinds of caller sit on opposite sides of the animation.** `triggerMoveEffects(..., landingDelayMs)` fires the come-out / home / all-home chimes, the bump sound and the bumped peg's fly-back. An AI move calls it *after* its peg has finished gliding, so it passes 0. A human move calls it *before* the cosmetic replay, so it passes `landingDelayFor(...)` — without that, at the slow pace the "peg is home" chime lands three seconds before the peg does, and the peg you were about to bump gets knocked back to start while your peg is still two-thirds of the way over to it. `landingDelayFor` is `(path.length - 1) * stepMs`, **not** `path.length * stepMs`: `animateMove` draws `path[k]` at `k * stepMs`, so the peg is standing on its destination a whole step before the interval clears, and a bump one step late reads as the target flinching after the fact. The deferred chime timers live in `arrivalTimersRef` and are cancelled everywhere the game can end or change, for the same reason the status line has no timers left: a chime that fires after the result banner is the same class of bug.

**A bumped peg is held on its space until it is actually hit — `runBumpFx(..., holdMs, onImpact)`.** For the whole `holdMs` the peg is drawn, unchanged and unglowed, on the space the board says it has already left; only at impact does it take the red (or green, for a friendly bump) glow and fly. Three things make that work and all three are load-bearing: `bumpHoldRef` holds the pre-impact timeout and must be cleared everywhere `bumpFxRef` is (a stranded hold fires a bump sound into the next game); `onImpact` fires from the same timer as the fly-back so sound and picture cannot drift apart; and `isPegBumping(player, pegIndex)` blanks the peg's start slot *and* its track space for the duration, the way `isPegAnimating` does for a gliding peg — without the track half, a friendly bump (which lands on the track, not in a start slot) drew two of the peg.

An AI split is the one move whose effects still play once, at the end, rather than per half: the board isn't committed until both halves have animated, so a bump played after the first half would fly the peg away and then have it pop back onto the space it started from when the FX ended. Fixing that properly means committing the board mid-split, which is a save-state question, not an animation one.

**Sounds say who, not just what.** `PLAYER_TONES` gives each seat a base pitch (C5/G4/D#5/A4) that every per-seat sound is built from, so you can tell Blue's peg from Pink's without looking. Bumps are three sounds, not one — `bumpDelivered`, `bumpReceived` (lower, longer, heavier haptic; being knocked back is the worst thing in the game and it used to sound identical to doing it to someone else) and `friendlyBump` (bright and rising, because in partner mode it's a *good* move). `home` chimes per peg; `allHome` is a bigger flourish for a seat's fifth, deliberately smaller than `win` since in partner mode it can happen half a game early. `grumble` (the muttering under a knocked-back peg's "@$#*!" bubble) is pitched from the *victim's* tone, and is deliberately unmusical — four short detuned sawtooth blips; `fanfare` belongs to the "Double Play!" banner.

**The three things that happen with nothing to watch get said out loud.** `src/game/announce.js` is the pure derivation: given the engine's own knock-back diff (`findBumps`) and the friendly half of a move's `displacements`, plus the one thing neither can tell you (`isJoker` — a joker's effect on the board is indistinguishable from any other bump), it returns which banners a move earns. **Joker!** (its animation path is empty by construction, so the board simply rearranges itself), **Partner Bump!** (looks like an ordinary nudge unless you already know the rule) and **Double Play!** (`bumps + friendly >= 2` — two pegs displaced by one card, so whichever one you were watching is the one you missed). They *stack* rather than replace: one card can legitimately be all three, and last-one-wins would silence exactly the flashiest move in the game.

**A friendly partner bump is *reported* by the engine, never diffed off the board.** `applyMove` / `applyJoker` / `applyComeOut` return `displacements` — `{ player, pegIndex, fromPosition, toPosition, friendly, byPlayer, byPegIndex }` per peg the move shoved, in causal order — and `triggerMoveEffects` takes that list. Knock-backs stay diffed (`findBumps`), because a peg going track → start can't be anything but a bump; friendly bumps cannot be, and the old `findFriendlyBumps` got *both* interesting cases wrong. It recognised "a peg on its owner's home entrance that isn't the mover", but the entrance is the last track space before the home corridor and so an entirely ordinary place to land under your own power: a split moves two pegs and only one was ever named, so the second half's perfectly normal arrival raised a phantom **"Partner Bump!"** — banner, green fly-back and chirp — over a space no partner had ever been on. And the entrance swap displaces *the mover itself*, which any diff must exclude as "the peg that meant to move", so the fanciest partner bump in the game announced nothing at all. `getPossibleMoves` carries `displacements` on every AI move shape (both halves' worth for a split) for the same reason. Don't reintroduce a diff here.

Two things about the wiring matter. They fire on the **same `landingDelayMs` as the bump sound** — a banner that appears while the peg causing it is still counting its way across the board reads as a banner about the *previous* move. And the fanfare fires from inside `announce` itself, at the moment the banner is inserted, for the same reason `runBumpFx` fires its sound from the fly-back timer: one timer means sound and picture can't drift apart. Every banner is a timer, so `clearAnnouncements` is called from every place the animation and bump timers are cancelled — `endGame`, new game, `clearBoard`, `applySavedGame`, `startReplay` and unmount. A banner that outlives its game is the same class of bug as the status-line timers that used to print "Blue is thinking…" under a win banner.

**Every peg a card displaces flies — `runBumpFx` takes a list.** A partner bump onto an entrance an opponent is sitting on moves *two* pegs, and animating only the first left "Double Play!" describing something the board never showed: the peg you weren't watching simply teleported. So the fx state is `{ holding, tick, items }` and all of them run off one interval, staggered by `stageBumpFlights` (`anim.js`, tested) — friendly shove first, then whoever it knocked off the entrance, so the chain reads in causal order. The stagger is deliberately shorter than a flight so a cascade overlaps into one event rather than queueing into two; with a single peg the staging is byte-for-byte the animation it replaced. Each item carries its own `onImpact`, fired as *its* flight starts, so a cascade is a chirp and then a thud in the order you watch it — the old code played one sound for the whole move. `isPegBumping` covers every peg in the list, including one still waiting its turn, which is drawn unglowed on the space the board says it has already left.

**Pegs talk — `showBubble`.** Two exchanges, one overlay. A peg knocked back to start complains about it (`showBumpTaunt`): A cartoon "@$#*!" bubble in the peg's own colour, plus `sfx.grumble`, over the slot it was sent back to. It fires when the fly-back *finishes*, not at impact: the complaint belongs over the peg where it lands, and at impact the peg is still in mid-air. It is the one piece of feedback aimed at the *victim* rather than the mover, and a list for the same reason the fly-back is: send two pegs home with one card and both have something to say. Positioned from `getStartAreaPosition`, so it follows the board rotation for free. It renders in **its own overlay SVG** (same `viewBox` over the same box, `z-20`) rather than inside the board, purely so it sits above the banners — a cascade raises a banner and a bubble at the same moment, and drawn inside the board the bubble ended up underneath the very message telling you to look at it. It still shows with animations off — it is feedback, not travel, and that setting is precisely where a peg vanishes from the track and reappears in a start area with nothing in between. The `pnj-taunt` keyframe duration in `index.css` must match `TAUNT_MS`, which is what actually removes it.

A partner bump gets the opposite exchange (`showPartnerThanks`): the peg carried to its own home entrance says **"Thanks!"** as it lands, and the peg that put it there answers **"You're welcome!"** a `REPLY_MS` beat later — short enough that both are on screen together, which is what makes it read as one exchange rather than two pegs muttering. Which peg says which is *not* always the obvious way round, and this is why the engine names `byPlayer`/`byPegIndex` on the displacement: in the entrance swap it is the **mover** that gets the free ride, so the mover thanks the partner that never moved. Reading the speaker off the displacement means the swap needs no special case in the component. Both bubbles sit over track spaces, so the bubble's `spot` is symbolic — `{ area: 'start', pegIndex }` or `{ area: 'track', position }` — and resolved through `getStartAreaPosition`/`getTrackPosition` at render time, keeping the board rotation free. The bubble sizes itself from its text (and drops a point of type past nine characters) so "You're welcome!" doesn't span a quarter of the board, and clamps its x so a bump on the outer track can't push it off the SVG. `runBumpFx` no longer knows about any of this: each fx item carries an `onLand` callback, the counterpart to `onImpact`, fired when *that* peg's flight ends.

**The card that was played is shown, on the board — `nowPlaying` + `renderPlayedCard`.** The board only ever showed a move's *effect*; knowing an opponent just spent their King is half of following the game. So each move raises an overlay over the middle of the board: a large face-up card in the mover's colour, which pops, holds and then drops onto that seat's discard pile. It used to carry a caption pill above it (`Blue — Space 20 to Space 25`); those words are the status line now (below), because two captions for one move — one of them floating over the piles in the busiest part of the board — was one too many. `showNowPlaying` — not `setNowPlaying` — is what the two move sites call: it stamps an `id` so the entrance animation replays for every move (two identical moves in a row would otherwise reuse the DOM node and animate once), and carries `lifeMs`, the move's own travel + settle time. The card's flight is scaled to `lifeMs` (floored/capped by `PLAYED_CARD_MIN_MS`/`MAX_MS`) because the overlay is unmounted the instant the move ends: a fixed flight leaves a one-space move's card hanging in mid-air halfway to the pile, and a card that vanishes instead of landing is worse than one that never moved. The fly target comes from `DISCARD_SLOTS`, the same table the piles are drawn from, so it follows the board rotation; `PLAYED_CARD.cx/cy` is duplicated as the `transform-origin` of `.pnj-card-play` in `index.css`, which is the one coupling to keep in step.

**Both of these are overlays, and that is the point.** This used to be two boxes in the page flow above the board — a bordered "Blue played 7♠" panel and a "Recent moves" list. On a phone the panel appeared and vanished with every single move, shoving the board down the screen and yanking it back up a second later, and the list ate the space the board needed. For anyone not already fluent in the game, a board that jumps around is worse than no commentary at all. Drawn over the board (same `viewBox`, `pointer-events-none`, like the taunt overlay), they cost no layout: nothing moves. The move log is gone entirely — the board rim already carries each seat's last move. **Don't put commentary back into the page flow.** Its `aria-live` region isn't lost: the status box is one, and it now carries the same sentence.

**The status line is the commentary — `describeStatusParts`.** Everything that wants to tell you what is happening goes through the one box above the board, because it is the one box that is *always there*. `describeStatus` takes a `moving` flag so it reads "Blue is moving…" once a peg is actually travelling rather than "Blue is thinking…" over a peg visibly counting its way around — and, given the move on screen, it says the strictly more useful thing instead: **"Blue played 7♠ — Space 20 to Space 25"**. Same for a running replay: `📺 Replay 2/3 Blue — …`. Three consequences, all deliberate:

- **A prompt outranks commentary.** Mid-split, mid-joker and mid-discard the line is an instruction waiting on a tap, and it stays one — the first half of a split animates while the second half still needs a peg, and describing the peg you can already see would cost you the words you actually need.
- **`describeStatusParts` returns parts, not a string** (`prefix` / `player` / `who` / `detail` / `text`) so the seat's *name* can be drawn in the seat's colour. `describeStatus` is `.text`, which is what the tests assert and what a screen reader hears; there is one derivation, so the two can't drift.
- **The box reserves two lines and clamps at two** (`min-h-[3.5rem]`, `line-clamp-2`). It is now the one element on the page whose text length changes with every move, and left to size itself it would grow and shrink under the board — reintroducing exactly the jumping the overlays exist to prevent. The corollary: the played-card overlay has no `sr-only` companion any more, because a second `aria-live` region carrying the same sentence would read every move twice.

**Nothing else appears and disappears above the board either.** The instant-replay button and its playback banner used to live between the status box and the board, arriving the moment your turn came round and leaving when the replay ended — each one shoving the board down the screen and pulling it back. Both are now the 📺 button in the header, which is *always mounted* (disabled and dimmed at 40% when there is nothing to watch, badged with the move count when there is, ⏹ Stop while a replay runs), and the replay's progress reads in the status line with everything else. `replayAvailable` only ever enables that button; it must never gate whether it renders.

### Ending a game

`endGame(winner, { winningSeat, description })` is the **only** terminal transition, called from `executeMove`, `completeSplit`, `completeAIMove` and `handleJokerTarget`. It cancels every pending timer (animation, bump FX, both replay timers, the first-player spinner and the AI's thinking timeout), sets `winner`, and records stats. Adding a new win-detection site means calling `endGame`, not `setWinner`.

Stats are recorded from the **terminal state**, keyed by game id — not by watching the `winner` transition, which only fires for whoever happens to be looking. Every game gets an id (`newGameId()` locally; it round-trips through the save so resuming keeps it), and `recordFinishedGame` is a no-op for an id already in `pnj:recordedGames:v1`. So a result is counted exactly once whether you were open when it landed, and whether the winning move was yours, your partner's or an AI's. `didIWin(winner, mode, mySeats)` decides whether it was a win for you — in partner mode `winner` is a team index, so this is what credits you when your *partner's* move wins.

**`endGame` reads the mode and the seats from refs (`gameModeRef`/`mySeatsRef`), never from the render closure**, and is therefore dependency-free and stable. A remote game can end on the *other* device, so `endGame` frequently runs from the fetch or listener that adopted the finished state — and those callbacks were created before the `setGameMode`/`setSeatOwners` that opened the game took effect. Reading `gameMode`/`mySeats` there saw the mount defaults (`classic`, `['me','ai','ai','ai']`), which filed a remote *partner* win in the **Solo** bucket and summed seat 0's joker/bump tallies for a guest who plays seat 2 (the win/loss itself came out right only by luck: `winningSeats(0, 'classic')` is `[0]`, and team 0 contains seat 0). `setGameMode` and `setSeatOwners` are wrappers that write ref and state together — the same discipline `setActiveSession`/`sessionRef` already used — so **always go through them**, and prefer the refs over the closure in anything a listener or an `await` can outlive.

### Remote play

Two humans play partner mode against two AI opponents, asynchronously, each on their own device. It is entirely optional and entirely additive: with no `VITE_FIREBASE_*` config, or on a device with no remote games, the app is byte-for-byte the solo game — same first-player modal, same single local save, same resume prompt — and never signs in or downloads the Firestore SDK. All of Packages 0–5 of `docs/multiplayer-phase1-plan.md` are built: turn exchange and automatic replay work end to end. Package 6 (a manual playtest matrix and a final docs pass) is the only thing left.

**Turn exchange (§4.1–4.3).** A `commitTurn` helper is the single place a human turn ends: it advances `currentPlayer` locally and, if a remote session is open, publishes exactly once — never mid-turn. It is called from the four real handoff sites (`executeMove`, `completeSplit`, `discardAndDraw`'s human branch, `handleJokerTarget`) and, as one addition beyond what the plan spelled out, from the AI effect's own `completeAIMove` **only when that AI move ends the game** — see "One thing the plan didn't cover" below. A half-finished split never crosses the wire: `commitTurn` always publishes `splitRemaining`/`splitCard`/`splitPegIndex`/`splitOwner` as cleared, so a disconnect mid-split simply restarts that turn from the pre-split state when the player returns. The published state's `winningSeat`/`description` (added to `buildPublishMeta`/`publishState` beyond the plan's original sketch) are how the client that didn't make the winning move still learns who made it and what it was — the shared `state` blob itself has no `winner` field by design (see below).

**The AI-simulation gate (§4.2).** `shouldSimulateAI(currentPlayer, seatOwners)` (`src/net/seats.js`) is `nextHumanSeat` + `ownsSeat` as one predicate: a client runs an AI seat forward only when the chain of AI seats starting there terminates at one of its own seats. Exactly one client is ever eligible for a given AI turn — the one that needs the move to reach its own turn — so nothing double-simulates and nothing double-publishes. In solo every chain leads back to seat 0, so the predicate is always true there and solo is unaffected. In a remote game this effect only ever runs as a *catch-up* simulation, never as a live continuation of the mover's own turn (the fixed human/AI/human/AI layout means the seat after your own move always leads to the *other* human, never back to you) — so `session != null` alone is the correct "run this silently" signal: no thinking delay, no animation.

**Per-seat stat tallies.** `jokersPlayed`/`bumpsDelivered`/`timesBumped` are `[n0, n1, n2, n3]` arrays, not personal totals — `triggerMoveEffects` used to gate them on `ownsSeat`, which silently broke the moment an AI's bump was simulated by the *other* client (that client's `ownsSeat` check would never be true for either side). Now whichever client actually simulates a seat's move records it at that seat's index, unconditionally; `endGame` sums only `mySeats` at record time to get "my" lifetime stats. `turns` stays a single shared counter, but is now incremented directly at each site a turn ends (including the winning move) rather than inferred from a `currentPlayer` transition — the old effect miscounted the moment an adopted remote state could jump `currentPlayer` by more than one seat. `startMode` is `null` for every remote turn (host and guest both) — "did I choose to go first" isn't meaningful once the host's deal is a fixed rule and the guest never chose — so a remote game counts toward neither the `chosenFirst` nor `randomFirst` stat bucket.

**Automatic replay (§5.1–5.2).** On adopting a remote state, `handleRemoteState` seeds the local replay buffer from the wire's `replay` frames (`seedReplay`/`appendReplayFrame`, `src/net/replay.js` — wire frames always play before anything this client simulates locally) and sets `pendingAutoReplayRef`. A silent AI simulation (no delay, no animation — the same `session != null` signal as the gate) may run after that; once it becomes this client's turn — or the game ends, if the win happened *during* that silent simulation and control never actually reaches this seat — the buffered frames auto-play at the normal replay pace, then unlock. `derivePhase` ranks `replaying` above `finished` (flipped from Package 1) and the end-of-game overlay is additionally gated on `!isReplaying`, so a remote win plays out before the result appears rather than under it. Skippable via the header's ⏹ Stop. Solo is unaffected: `pendingAutoReplayRef` is only ever set by an adopted remote state, so the AI still animates live there and the manual 📺 button is the only way to watch a replay. When animations are disabled, there is no auto-replay (nothing to watch) — a plain-text "Since your last turn" summary renders instead.

**Two replay buffers, not one — `replayLogRef` vs `replayOwnRef`.** `replayLogRef` is what a client should *watch*: the seed it adopted (its partner's move, forwarded through any AI hops) plus whatever it simulated locally — correct for the auto-play and the manual button. It is **not** what a client should *publish*. `commitTurn` publishes `replayOwnRef` instead: only the frames this client itself simulated since its last adopt, via `recordReplayFrame` (never touched by seeding). The reason: with exactly two humans strictly alternating publishes, the seed in `replayLogRef` is always *the recipient's own earlier move* — publishing it back re-forwards someone their own move, and the next hop does it again, so a buffer built from `replayLogRef` grows to "replay the whole game" within a few rounds. `replayOwnRef` is reset to `[]` everywhere a seed is adopted (`handleRemoteState`, `openRemoteGame`) and everywhere `replayLogRef` resets (hand-off, new game), and is appended to only alongside `recordReplayFrame`. Regression test: `src/net/replay.test.js`'s "two-buffer discipline across multiple hops".

**One thing the plan didn't cover:** what happens when a *silently-simulated AI move* ends the game. §4.2 says the AI effect's own player-advance "must stay purely local," folded into this client's next human publish — but a game-ending AI move has no next human publish to fold into, since this client's own turn never arrives. Without publishing there, the other player would never learn the game ended. So `completeAIMove` publishes directly in exactly that one case (still a no-op in solo), reusing the same `commitTurn` every human site uses.

**The security rules are the whole backend.** There is no server. `firestore/firestore.rules` is the only thing between the app's public config and the data, and it enforces one rule: you may read or write a game only if your anonymous uid is in its `participants`, with a single exception for an unclaimed `lobby` game (a joiner must read it to claim the seat, and it holds no state yet). The acceptance gate — a *different* anonymous uid can read neither an active game's metadata nor its `live/current` — is proven against the emulator in `firestore/rules.test.js` (`npm run test:rules`), which is the most important test in the package. `firestore/indexes.json` carries the one composite index the lobby query needs.

**Data model.** `games/{id}` holds small metadata only (participants, hostUid/guestUid, code, status, version, currentPlayer, `waitingOn`, winner, `winningSeat`, `description`) so the lobby can listen to it cheaply; the heavy blob lives in `games/{id}/live/current` (`state`, `replay`, `version`), which only the open game listens to. A turn writes both in one transaction, advancing `version` by exactly one — rule (b) makes the compare-and-swap a database guarantee. `codes/{CODE}` resolves a typed code to a game id (the id alone grants nothing). `state`/`replay` are stored as **JSON strings**: the game state is arrays-of-arrays (pegs/hands/discardPiles) and Firestore cannot store nested arrays — this is the one place the plan's "sync the whole `serializeGame()` blob" needed a correction. `state` never carries a `winner` field by design (the engine's win check runs on adoption, not on the wire), which is why `winningSeat`/`description` live in the metadata instead — it's the only way the client that didn't make the winning move learns who made it and what it was.

**Auth is anonymous and lazy.** `signInAnonymously()` mints a durable per-device uid with no UI. Sign-in and the SDK load happen only from a multiplayer action (create/join, opening the lobby, or a device that already has games) — see `src/net/firebase.js`. Verify the SDK stays out of the main bundle: it is a dynamic `import()` and lands in a separate chunk.

**Seat model.** A remote game swaps the solo `['me','ai','ai','ai']` for `['me','ai','them','ai']` (host, seat 0) or `['them','ai','me','ai']` (guest, seat 2). Everything else — board rotation, turn gating, actor identity — already derives from `seatOwners` (see "Seat ownership"), so the guest sees their own pegs at the bottom with no special-casing. `waitingOn` is `nextHumanSeat(currentPlayer, seatOwners)` and is written into the shared metadata; because seats 1 and 3 are `'ai'` in every layout, it is the same absolute seat from either client's point of view.

**The lobby (My Games).** A modal overlay, not a route, populated by one `subscribeMyGames` listener that feeds both the game list and the waiting-on-you badge. **"Your turn" is `waitingOn === seat`, never `currentPlayer === seat`** — a turn is published after it passes on, so every stored game is parked on an AI seat and the naive test is false for everything. Switching games reuses `applySavedGame` (switch ≈ resume a different save); it is blocked mid-split. The lobby opens on mount only when the device actually has remote games (`hasLocalGames()`), never merely because the env vars are set — that is what preserves the solo resume flow in production.

**Turn signalling.** `countWaitingOnMe` drives two things from one number: the badge on the My Games button, and — via a `useEffect` on `waitingCount` — the home-screen icon badge (`src/badge.js`). The icon badge is free: `setAppBadge` is a local OS call that makes no network request and costs nothing server-side, and the count is already derived for the in-app badge, so it adds no listener and no Firestore read. Two things about it are deliberate and must not be "fixed": **the effect has no cleanup function** (the OS keeps a badge until cleared, which is the point — close the app with a turn waiting and the icon still says so), and **it is only ever as fresh as the last time the app was open** (nothing runs while the app is closed, so an overnight move raises no badge and a turn played on another device leaves this one stale). That staleness is the ceiling of a no-backend signal; only a service worker woken by push can badge an app that isn't running, which is Phase 2. Don't close the gap with a polling timer or a background sync — that trades the whole "costs nothing" property for a signal that is still hours stale. Support is partial (no Firefox or desktop Safari; iOS needs an installed PWA *and* notification permission, which the app never requests today), so every call is a swallowed no-op by design.
**Opening a game always replaces the board — `clearBoard` is the counterpart to `applySavedGame`.** `openRemoteGame` branches on `openActionFor(...)` (`lobby.js`), which is pure and tested precisely because getting it wrong made two games look like one: only `adopt` has a state to show, and the other three answers (`deal`, `await_guest`, `await_deal`) mean the board must be **blanked**, not left as it was. It used to be left as it was — an undealt game fell through every branch, so switching from a game in progress to one still waiting for a partner kept the first game's board on screen, under the second game's session (a move there would have published to the wrong game). So `openRemoteGame` calls `clearBoard(seat)` up front, before the fetch: no stale board during the round trip, and none at all if the game turns out to be undealt. `clearBoard` empties the hands (so `dealt` is false and the phase is `dealing`), resets pegs/split/selection/tallies, cancels every timer, and parks `currentPlayer` on a seat this client owns so the AI-simulation effect doesn't reach for a hand that isn't there. `await_guest` additionally re-shows the host's code + invite link (`inviteLinkFor`), which is the only thing on screen that explains a deliberately blank board; that modal yields to the lobby (`hostInfo && !showLobby`) since both are z-50, so its "My Games" button can reach your other games.

**Listener discipline.** Detaching a Firestore listener on game switch and on unmount is the discipline that used to be "clear the interval" — a leaked listener bills forever. Every path that changes the open game goes through `detachGameListeners` first, and the component detaches all three listeners on unmount. Your own write echoes back through your own listener; `isEcho` (hasPendingWrites, or a version you already hold) ignores it.

**Setup.** `scripts/setup-firebase.sh` provisions a Firebase project (a human runs it — the agent has no Google credentials); it prints the four `VITE_FIREBASE_*` values, which go in `.env` locally and as GitHub Actions repository **variables** (public by design, not secrets — wired into `deploy.yml`). `npm run rules:deploy` redeploys the rules; `npm run emulators` runs the emulator suite for local dev (point the app at it with `VITE_FIRESTORE_EMULATOR_HOST` / `VITE_AUTH_EMULATOR_URL`).

`vite-plugin-pwa` (configured in `vite.config.js`, `registerType: 'autoUpdate'`) generates the service worker and web manifest at build time and precaches the built shell for offline play. Icons live in `public/` (`pwa-192x192.png`, `pwa-512x512.png`, `pwa-maskable-512x512.png`, `apple-touch-icon.png`, favicons) and were generated by `scripts/gen-icons.py` (Pillow). Manifest `start_url`/`scope` are relative (`.`) so install works from a GitHub Pages subpath.

## Testing

Tests live next to the modules they cover (`src/*.test.js`, `src/game/*.test.js`, `src/net/*.test.js`) and run with Vitest. They cover deck composition, move validation for every card type (including 7/9 split rules and home-corridor edge cases), bumping, win detection, AI move selection, seat-ownership derivations (including `nextHumanSeat`), board rotation, phase/status derivation (including the move commentary and replay progress the status line now carries, and the prompts that outrank them), idempotent stats recording, the animation pacing table and its persisted preference (including the bump fly-back's staggered staging), the peg-event diff behind the sounds, the banner derivation behind Joker!/Partner Bump!/Double Play!, and — for remote play — the game-code generator, the wire-document builders, the session client against a mocked Firestore, the local game store, and the lobby derivations. `vitest.config.js` restricts `npm test` to `src/**`, so the emulator-backed rules test is not part of it. CI (`.github/workflows/ci.yml`) runs `npm test` and the build on every pull request with no Firebase env vars — that is deliberately what a solo build must pass.

**The security rules are tested separately, against the emulator.** `npm run test:rules` starts the Firestore emulator (`firebase emulators:exec`) and runs `firestore/rules.test.js`, which is the acceptance gate for the backend: a client with the app's public config, signed in as a *different* anonymous uid, can read neither an active game's metadata nor its `live/current`. It is not in the default suite because CI has no emulator. `@firebase/rules-unit-testing` and `firebase-tools` are devDependencies so `npm run test:rules`/`npm run emulators` work out of the box (or install `firebase-tools` globally and prune them).

There is no component-test setup and none is planned: logic that needs testing belongs in a plain module, not in `PegsAndJokers.jsx`. The two-device flow that can only be seen through the component (host creates → guest joins by link → both land on a correctly-oriented dealt board) was verified with two Chromium/Playwright contexts driving the emulator; that harness is not committed.

## Game Logic Key Concepts

- Track positions: 0-71 (18 spaces per side × 4 sides)
- Start position: `player * 18 + 8` (position 8 on each player's side)
- Home entrance: `player * 18 + 3` (position 3 on each player's side)
- Cards A/J/Q/K allow moving from start; 7 can split forward; 8 moves backward; 9 must split (forward + backward); Joker bumps opponent

### Partner mode

Note that `checkWinner(pegs, 'partners')` and everything downstream of it return a **team** index, not a player index — `stats.js`'s `didIWin`/`winningSeats` are how that is interpreted, including crediting both members of the winning team in the nemesis stat.

Selectable at game start (Classic is the default). Players sit opposite in teams — you (Yellow) + Pink vs Blue + Green. The team wins when both partners have all pegs home. Bumping a partner is legal and *strategic*: instead of going to start, a friendly-bumped peg lands on its owner's home-entrance space (`player*18+3`), ready to go home. If that entrance is occupied by an opponent it cascades (opponent → start); if occupied by that owner's own peg the whole move is illegal (like landing on your own peg). Once your own pegs are all home, your cards move your partner's pegs. Classic mode is unchanged — the engine `options` default (`actor === owner`, `mode: 'classic'`) preserves the original behavior.
